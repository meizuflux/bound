**Bound implementation review — October 23, 2026**

The shared flight workflow and admin management are complete and suitable for
local evaluation. The main remaining public-launch gaps are abuse controls,
production email, and account recovery. The review found several real correctness
and interaction bugs; the fixes described below are included in the implementation.

Reviewed implementation: `0ce3874` (`add shared flight storage`) and `c9b63f7`
(`add flight picker and admin management`). Both commits use SSH signing.
Three implementation agents worked on the domain, student experience, and admin
management. Independent cross-reviews covered flight/admin code and the shared
authentication, audit, and rendering code; the parent performed integration and
browser verification.

**What is implemented**

- Flight search with delayed live results, inline creation, review/edit, duplicate
  handling, join/leave, My flights, revision-specific confirmations, and corrections.
- Shared identities that exclude departure time. Reviewed alternate numbers,
  separate departure instances, transactional merges, and permanent old-link redirects.
- Admin user creation, role/suspension updates, session revocation, and confirmed
  deletion. Account email stays immutable. Admin-created users still verify their
  school email; their creation does not replace the administrator's session.
- Admin flight creation/editing, archive/restore, alternate-number management,
  correction approval/rejection, and merge preview/confirmation.
- Attributed activity history with retained actor/account/flight snapshots.
  History is append-only through the application. Flight deletion is an archive;
  account deletion removes the account while retaining its historical events.

**Findings that remain**

P1 means address before a broad public deployment; P2 is a functional limitation
or important operational follow-up; P3 is a scaling or maintenance improvement.

| Priority | Finding and evidence | Recommended next step |
| --- | --- | --- |
| P1 | Password work and writes have no application-level attempt limits. Signup/signin use unrestricted `spawn_blocking` for Argon2; verified users can submit distinct flights and correction proposals repeatedly. See [authentication](/Users/ryan/Projects/meizuflux/bound/src/auth.rs:381) and [correction writes](/Users/ryan/Projects/meizuflux/bound/src/flights/data.rs:552). Input bounds, verification, and duplicate prevention do not bound CPU use or distinct submissions. | Bound password-work concurrency; enforce account/IP login limits and per-account creation/proposal quotas server-side. Define trusted-proxy handling before using forwarded client addresses. |
| P1 | Email remains the existing local Mailpit integration, using an unauthenticated plaintext SMTP transport. See [mailer](/Users/ryan/Projects/meizuflux/bound/src/mail.rs:23). This is appropriate for development and cannot serve as the production verification setup. | Configure and test authenticated production delivery, sender identity, failure handling, and HTTPS `APP_URL` before inviting real students. |
| P2 | A supported user who forgets their password has no recovery flow. Existing accounts are otherwise deliberately immutable by email. | Add a single-use, expiring password-reset workflow and revoke old sessions on reset; do not use admin-known passwords as the normal recovery process. |
| P2 | A valid departure in a repeated daylight-saving hour cannot be added, even by an admin. Example: RDU, November 7, 2027, 01:30. | P2 | Coverage is deliberately limited to [28 US airports and eight airlines](/Users/ryan/Projects/meizuflux/bound/src/flights/catalog.rs:15), with Duke as the supported school. Retain community provenance; an eventual provider can add another source without replacing membership identity. Live lookup is optional, not a prerequisite for the crowdsourced model. |
| P3 | [Activity search](/Users/ryan/Projects/meizuflux/bound/src/admin/data.rs:107) scans concatenated text with `lower`/`strpos` and uses offset pagination. Returned rows are bounded, but scanned rows can grow with history. [Flight lists](/Users/ryan/Projects/meizuflux/bound/src/flights/data.rs:191) use correlated counts and a multi-purpose query. | Benchmark representative data with `EXPLAIN (ANALYZE, BUFFERS)`; introduce indexed search, purpose-specific queries, and keyset pagination when measurements justify them. | P3 | [Identity-changing operations](/Users/ryan/Projects/meizuflux/bound/src/flights/data.rs:931) share an advisory lock. This makes creates, edits, aliases, and merges safe, but serializes those operations across unrelated flights. Membership operations remain independent. | Monitor lock waits and connection-pool saturation. Move to a documented per-identity lock order when measured write volume warrants the added complexity. |
| P3 | Expired sessions and historical events have no pruning/retention procedure. | Define retention and a tested maintenance process. Do not silently delete audit history as an optimization. |

**Bugs and quality issues fixed during review**

- Real HTMX 4 requests send targets such as `div#flight-results`, not a bare ID.
  The original comparison caused entire search screens to nest inside the results.
  [Shared target parsing](/Users/ryan/Projects/meizuflux/bound/src/templates.rs:26)
  and regression tests now use the installed library's actual header format.
- HTMX Back/Forward restoration requests need the full document. Returning only a
  panel could remove the header, footer, and skip link. `PageView` now honors full
  and history requests; partial navigation includes an updated document title.
- Panel replacements previously lost keyboard focus. A small shared enhancement
  focuses the relevant error or heading after navigation, while search results,
  membership cards, and polling summaries leave focus alone.
- An in-flight signin could create a session after suspension revoked existing
  sessions, allowing that session to reappear after restoration. Session creation
  now locks/rechecks account access. Account switching and signout follow a
  user-before-session lock order to avoid reversed-lock failures with revocation.
- Identity and alias changes could race. Creation/edit/alias/merge operations now
  serialize identity changes and reject collisions. Unrelated routes/dates cannot
  be merged accidentally.
- A merged historical record could reserve an identity after its destination
  flight changed. Migration 0010 limits uniqueness to canonical records, preserving
  history without blocking a later legitimate departure.
- Archived memberships disappeared from My flights. They now remain visible to
  their members, with removal available and new joins/confirmations disabled.
- Stale corrections cannot overwrite newer revisions. Merges preserve memberships
  and invalidate old confirmation evidence. Pending proposals appear ahead of
  reviewed history in the bounded student view.
- Admin errors preserve aliases, associate errors with forms/fields, and use
  validation/conflict statuses consistently. Archived/merged records hide actions
  that cannot succeed. The inline creation form avoids duplicate navigation and
  top-level headings and preserves its review/edit context.
- Audit writes now fail if the actor disappeared rather than silently dropping
  the event. Additional user-reference indexes support account deletion and
  session revocation without avoidable full-table scans.

**Modularity and backend quality**

The main boundaries are appropriate: HTTP handlers select responses, typed views
own presentation, shared flight operations own transactions, the catalog owns
supported codes/time zones, and the audit helper owns attribution. Admin calls the
same domain operations as student routes rather than rebuilding flight rules.
The existing local Askama adapter and escaped typed-template boundary are retained.
The shared five-connection pool is reused throughout.

The largest maintenance concern is the roughly 960-line flight data module. Its
public API is cohesive, but validation, queries, membership writes, moderation,
aliases, and merging now share one file. Before substantial further flight work,
split these into focused internal modules while keeping the current API and
transaction ownership. Dense template lines could also be formatted for easier
review; this does not require introducing another frontend framework.

Authorization is checked at the route boundary and again under transaction locks
for mutations. Inputs are bounded and normalized; queries bind parameters. Review
did not identify an SQL-injection, template-escaping, CSRF, or ordinary authorization
bypass in the exercised flows. That is a scoped review result, not a penetration
test or a guarantee about all possible behavior. Account/flight revisions and the
last-admin/self-access checks prevent the reviewed stale-write and lockout cases.

**UI assessment**

The warm paper/green style is consistent with the app. Search preserves its
controls, joining updates one card, creation reveals a focused form, and corrections
show current/proposed values together. Native inputs, explicit labels, error
associations, keyboard focus, loading indicators, and normal form fallbacks keep
the interaction usable without a client-side state framework.

Phone-width forms reflow without horizontal page overflow; wide tables scroll
within their own container. Manual browser checks covered the student-to-admin
correction workflow, review/edit preservation, navigation titles/focus, and browser
history. The last inline-layout and correction-response refinements also have
HTTP regression coverage. A full automated accessibility audit and screen-reader
session were not performed.

Useful next polish: field-specific controls for corrections instead of the generic
value field, friendlier time-zone labels, and concise loading text for every admin
mutation. Traveler discovery currently exposes same-school counts, not profiles,
contact details, or messaging; those are separate product work.

and recovery, then catalog/UX expansion. Measure real usage before redesigning the
locking or query strategy.
